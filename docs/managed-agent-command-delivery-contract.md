# Managed-Agent Command Delivery Contract

Status: proposed V1 target (partial Auspex implementation)
Owners: Auspex supervisor (client), Omegon control plane (server)
Protocol schema: managed-agent supervisor schema 1; delivery envelope schema 1

## Implementation status

Auspex currently implements stable command IDs, typed acknowledgement validation, correlated acknowledgement routing, same-payload replay, terminal and retryable rejection states, and result-before-ack delivery proof. It also prevents late acknowledgements from changing a terminal delivery state.

Auspex does not yet implement the `Queued` and `Sent` states, write-success tracking, the timeout and exponential-backoff policy, or connected-only replay. It also does not implement command-ledger eviction or run failure on terminal delivery rejection. Omegon deduplication and acknowledgement emission are external requirements. The requirements below define the V1 target and must not be read as a statement of current conformance.

## Purpose

A successful write to Auspex's local WebSocket outbox is not proof that Omegon received or accepted a managed-agent command. This contract adds application-level delivery identity, acknowledgement, retry, and deduplication without conflating delivery with operation completion.

## Required properties

1. Every managed-agent control command has a globally unique `command_id` generated by Auspex.
2. Omegon emits a typed delivery acknowledgement only after the authenticated WebSocket handler has parsed the full command, validated its delivery envelope, and admitted it to the named control-method handler.
3. A delivery acknowledgement does **not** mean the delegate operation completed. Existing method-specific results remain authoritative for operation state.
4. Auspex retains an unacknowledged command until acknowledgement, terminal rejection, or delivery timeout.
5. After reconnect, Auspex retries unacknowledged commands with the same `command_id` and identical payload.
6. Omegon deduplicates by `(authenticated_session, command_id)`. A duplicate never executes the operation twice; Omegon replays the original acknowledgement.
7. A reused `command_id` with a different payload is rejected as `command_id_conflict` and never executed.
8. Acknowledgements are correlated to `command_id`, `managed_run_id`, `worker_id`, method, and (when known) `task_id`.
9. Delivery state is bounded. Both peers may evict terminal acknowledgement records after the retention interval, but retries within the interval must remain idempotent.
10. Secrets, raw prompts, and full results are never copied into acknowledgement envelopes or logs.

## Managed command request fields

All four existing managed-agent requests add these required fields:

```json
{
  "schema_version": 1,
  "command_id": "018f...uuid",
  "managed_run_id": "018f...uuid",
  "worker_id": "018f...uuid"
}
```

`delegate_get`, `delegate_result`, and `delegate_cancel` also retain required `task_id`. Method-specific fields are unchanged.

`command_id` is a UUID string. It identifies one delivery attempt lineage, not a run. A retry uses the same ID. A later poll uses a new ID.

## Delivery acknowledgement envelope

Omegon emits one flat WebSocket event:

```json
{
  "type": "managed_agent_command_ack",
  "schema_version": 1,
  "command_id": "018f...uuid",
  "method": "delegate_get",
  "managed_run_id": "018f...uuid",
  "worker_id": "018f...uuid",
  "task_id": "delegate_7",
  "status": "accepted",
  "rejection": null,
  "accepted_at_unix_ms": 1750000000000
}
```

Fields:

- `type`: exactly `managed_agent_command_ack`
- `schema_version`: exactly `1`
- `command_id`: exact request identity
- `method`: one of `delegate_dispatch`, `delegate_get`, `delegate_result`, `delegate_cancel`
- `managed_run_id`, `worker_id`: exact request identities
- `task_id`: null only for pre-acceptance dispatch
- `status`: `accepted` or `rejected`
- `rejection`: null when accepted; structured rejection when rejected
- `accepted_at_unix_ms`: server observational timestamp; not used for deadlines

Structured rejection:

```json
{
  "code": "unsupported_schema",
  "safe_message": "managed-agent command schema 2 is unsupported",
  "retryable": false
}
```

Required rejection codes:

- `unsupported_schema` — terminal
- `invalid_envelope` — terminal
- `unauthorized` — terminal for the current credentials
- `unknown_method` — terminal
- `command_id_conflict` — terminal
- `overloaded` — retryable
- `temporarily_unavailable` — retryable

Method-level domain rejections (unknown task, policy denial, invalid state) remain in the existing method-specific result envelope. Delivery may be accepted while the operation is rejected.

## Omegon processing order

For each authenticated managed-agent command:

1. Parse the common identity fields and method.
2. Validate schema and UUID syntax.
3. Compute a canonical payload digest over the complete command excluding transport framing. Recommended: SHA-256 over canonical JSON.
4. Look up `(authenticated_session_identity, command_id)` in the delivery dedupe store.
5. If found with the same digest, replay the stored acknowledgement and do not invoke the method handler.
6. If found with a different digest, emit `command_id_conflict`; do not invoke the handler.
7. Admit the command to the method handler.
8. Persist the accepted acknowledgement before or atomically with handler admission.
9. Emit `managed_agent_command_ack`.
10. Emit the existing method-specific result independently when available.

If steps 7–8 cannot complete, emit a retryable rejected acknowledgement and do not invoke the handler.

## Auspex state machine

Per command:

```text
Queued -> Sent -> Acknowledged
             \-> RetryPending -> Sent
             \-> DeliveryRejected
             \-> DeliveryTimedOut
```

Rules:

- `Sent` starts a monotonic acknowledgement deadline (default 5 seconds).
- Disconnect changes `Sent` to `RetryPending`; reconnect retransmits using the same ID and payload.
- Retryable rejection changes state to `RetryPending` with bounded exponential backoff.
- Terminal rejection changes state to `DeliveryRejected` and emits a run-level supervisor failure/event.
- Expiration after the command delivery deadline changes state to `DeliveryTimedOut`.
- A method-specific response may arrive before its ack. Receipt of a valid, fully correlated method response implicitly proves delivery and may satisfy the pending ack, but Auspex still accepts a later duplicate acknowledgement idempotently.
- Duplicate acknowledgements are no-ops after correlation validation.
- An acknowledgement arriving from an instance other than the run's recorded instance is rejected.

## Retry and retention policy

Auspex defaults:

- acknowledgement timeout per send: 5 seconds
- retry delays: 250 ms, 500 ms, 1 s, 2 s, 4 s (cap)
- overall delivery deadline: bounded by the earlier of 30 seconds or the run supervisor deadline
- retries occur only while the authenticated instance transport is connected

Omegon defaults:

- dedupe retention: at least 10 minutes and at least the configured maximum delegate wall timeout plus 60 seconds, whichever is greater
- bounded LRU/TTL storage
- dedupe records contain identities, payload digest, and acknowledgement only; never raw result content
- dedupe records must survive WebSocket reconnects within the same Omegon process

Process restart semantics: V1 may lose dedupe state across Omegon process restart. Omegon must then reject retries for stale task-bound commands safely when normal task identity/state validation fails. Durable cross-process exactly-once execution is explicitly out of V1 scope.

## Ordering and races

- Ack and method result ordering is not guaranteed.
- Auspex must accept result-before-ack.
- A disconnect after Omegon admission but before ack emission is recovered by same-ID retry and acknowledgement replay.
- A disconnect before admission causes retry and first execution.
- Late responses after a terminal run are validated, recorded diagnostically, and must not mutate terminal state.
- Cancellation remains two-phase: delivery ack, then `delegate_cancel_result` acknowledgement/termination state.

## Security requirements

- Dedupe key is scoped to authenticated session/tenant identity, never global command ID alone.
- Ack identity fields are copied from validated typed request fields, not untrusted loose JSON.
- Payload digest uses a collision-resistant digest.
- No acknowledgement logs raw directive, scope contents, model credentials, result, or cancellation details beyond bounded safe rejection text.
- Safe rejection text maximum: 1 KiB.
- Unknown fields follow existing serde policy; identity and schema fields remain required.

## Acceptance scenarios

### Normal delivery
Given an authenticated connected Auspex session
When Auspex sends a valid `delegate_get` with a new command ID
Then Omegon emits an accepted acknowledgement with matching method/run/worker/task identities
And invokes the get handler once
And later emits the method result.

### Lost acknowledgement
Given Omegon admitted a command and persisted its acknowledgement
And the socket disconnects before Auspex receives it
When Auspex reconnects and retries the identical command with the same ID
Then Omegon replays the stored acknowledgement
And does not invoke the handler again.

### Conflicting reuse
Given a command ID was admitted with payload A
When the same authenticated session sends payload B under that ID
Then Omegon emits terminal `command_id_conflict`
And invokes no handler.

### Result before acknowledgement
Given a method result reaches Auspex before its delivery acknowledgement
When identities match the pending command and run
Then Auspex treats delivery as proven and applies the method result once
And a later matching ack is an idempotent no-op.

### Cross-instance injection
Given run R is routed to instance A
When instance B emits an acknowledgement carrying R's IDs
Then Auspex rejects it before command or run state mutation.

### Retryable overload
Given Omegon cannot admit a command because its bounded queue is full
When it emits `overloaded` with `retryable: true`
Then Auspex retries with the same command ID and payload after bounded backoff.

### Delivery timeout
Given no acknowledgement or correlated method result arrives before the overall delivery deadline
When the monotonic deadline expires
Then Auspex marks the command `DeliveryTimedOut`
And records one bounded supervisor diagnostic
And does not claim the remote operation terminated.

## Auspex implementation scope

- Add `ManagedCommandId` UUID newtype.
- Add required `command_id` to all managed-agent request DTOs.
- Add typed `ManagedAgentCommandAck` and rejection DTOs.
- Add pending-delivery ledger to `ManagedAgentSupervisorRuntime` with immutable serialized payload, route, state, monotonic timers, and retry count.
- Change event-stream outbox entries from raw strings to identified command records so successful socket writes can mark `Sent` without claiming acknowledgement.
- Demultiplex `managed_agent_command_ack` alongside method results.
- Retry pending deliveries after typed reconnect.
- Add adversarial tests for lost ack, same-ID replay, conflict, result-before-ack, cross-instance ack, duplicate ack, timeout, and retryable rejection.

## Omegon implementation scope

- Parse `command_id` on all four supervisor methods.
- Add authenticated-session-scoped bounded dedupe store.
- Canonicalize/digest command payloads.
- Atomically persist accepted ack with handler admission.
- Emit flat `managed_agent_command_ack` events.
- Replay ack for identical duplicate; reject conflicting reuse.
- Add fixtures and tests for every acceptance scenario above.
- Preserve all existing flat method-result envelopes unchanged except for accepting the new request field.

## Out of scope for V1

- Durable exactly-once delivery across Omegon process restart
- Cross-host distributed dedupe
- Ordering guarantees between acknowledgement and result
- General acknowledgement wrapping for non-managed commands
- UI projection
